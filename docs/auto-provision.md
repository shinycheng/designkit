# 自动开通生图额度（Sub2API 代客建号）

> 面向管理员。看完这一篇，你应该能自己把它配好、测好、以及在它出问题时知道下一步做什么。
> 不需要懂技术，也不需要看代码。

---

## 一、这是什么，以及它**不是**什么

**它是什么**：新建一个成员账号时，系统自己跑到图片网关（Sub2API）那边，
替这个人开一个账号、领一把只属于他的 API Key，存进来。
这样他一登录就能生图，费用从他自己的额度走。

**它不是什么**：

- **不是唯一通路。** 「成员账号」页那个「配置生图 Key」的手工入口永远保留、永远可用，
  而且永远比自动开通快。自动开通只是**省掉你去网关后台复制粘贴那一步**。
- **不是必须开的功能。** 默认是关着的。关着的时候，系统跟以前一模一样：
  你建号、你去网关后台开号、你把 Key 粘进来。
- **不是「开了就永远没事」。** 它一定会有一小撮人开不通（见第六节），
  这是设计里就认了的，不是故障。

**最重要的一条**：自动开通**开不通不影响任何人登录和使用**。
哪怕网关整个断电、地址填错、Key 过期，表现也只是「新成员照常进得来，
只是生图要等你手工发一把 Key」，绝不会变成「新人一个都进不来」。

## 二、开始之前，先确认两件事

**第 1 件：你打算让每个人花自己的钱吗？**

自动开通给每个人发一把**他自己的** Key。但这把 Key 要真的被用上，
「系统设置 → 图片访问与多用户 →『生图费用怎么算』」必须是**「每人一把 Key（各花各的）」**。

如果这里还是默认的「共用一把 Key」，那么自动开通照样会跑、Key 照样会发下来，
但所有人生图用的仍然是「生图服务」那一节里的全局 Key，费用还是记在一起。
——**不是 bug，是这两个开关本来就是分开的**（详见 README 的 7.4 节）。

**第 2 件：网关管理员 Key 得你自己去拿。**

这把 Key 是整台网关的最高权限。本项目的规矩是：**密钥一律由你自己在网页界面上填，
不写进代码、不写进配置文件、不写进 `.env`、文档里也不会出现任何一把真实的 Key。**
你要做的是登录网关后台，自己生成一把管理员 Key，然后粘到 DesignKit 的设置页里。

填进去之后，界面上就只显示一排星号了——**不显示末 4 位，也没有「查看」按钮**。
想换就把新的整串重新粘一遍；不动它直接保存，系统会认为「没改」，不会把原值覆盖成星号。

## 三、怎么配（一次性，大约 3 分钟）

管理员登录 → 左侧「系统设置」→ 往下翻到**「网关自动开通」**这一节
（在「图片访问与多用户」和「账号安全」中间）。

从上往下填：

| 填什么 | 填成什么样 | 填错了会怎样 |
|---|---|---|
| **自动给新成员开通** | 先别打开，等下面四项填完再回来打开 | 没填齐就打开，会被拦住并告诉你缺哪一项 |
| **网关地址** | 网关**管理后台**的地址，例如 `http://192.168.31.235:3000` | 见下面的 ⚠️ |
| **网关管理员 Key** | 你在网关后台自己生成的那一把，整串粘进来 | 开通全部失败，提示「管理员 Key 无效或没有权限」 |
| **目标分组 id** | 一个数字，就是网关后台里那个分组的编号 | 号建出来了、Key 也发了，但一张图都发不出去（提示「没绑分组」） |
| **成员邮箱后缀** | 默认 `designkit.local`，不用改 | 见下面的第二个 ⚠️ |
| **保管成员在网关的登录密码** | **保持关闭**（默认，更安全，理由见第七节） | 开着不会坏，只是安全上更吃亏 |
| **最多自动重试几次** | 默认 5，范围 1–10 | 填小了卡住的人更早转手工，填大了多熬几个小时 |

⚠️ **网关地址和「生图服务」那一节填的地址不是同一个。**
「生图服务」里填的是**发图**的地址（通常带 `/v1`，例如 `http://192.168.31.235:8090/v1`）；
这里填的是**管理后台**的地址（不带 `/api`、不带 `/api/v1`、不带问号后面的东西）。
把接口文档上那种 `http://…/api/v1` 的地址贴进来是最常见的错法——
保存时会被当场拦住并告诉你去掉尾巴。

⚠️ **成员邮箱后缀**：系统会用「dk + 成员编号 + @这个后缀」在网关那边建账号，
例如第 7 个成员是 `dk7@designkit.local`。这个邮箱不用真实存在、也不会收信。
只能用小写字母、数字、减号和点，中间要有一个点；
**不能以 `.invalid` / `.localhost` / `.example` / `.test` 结尾**（网关把这几个当保留后缀，
会直接拒绝建号，而报错里看不出是后缀的问题）；也不能带 `@` 和 `+`
（带 `+` 的邮箱会被网关当成同一个人的别名合并，两个成员会共用一个远端账号，账单直接算错人头）。

填完 → 点这一节的**「保存此区域」** → 再回到最上面把「自动给新成员开通」打开 → **再保存一次**。

> 部署在 NAS 上时还有一条：**跑 DesignKit 的那台机器要能连到网关后台的端口**
> （通常是 3000，和发图用的 8090 是两个端口）。连不上的表现是所有人卡在「开通中」，
> 原因写着「连不上网关」。在 NAS 上 `curl http://网关地址:3000/api/v1/settings/public`
> 试一下就知道通不通。

> 「连接超时」和「校验 https 证书」这两项目前没有界面入口，保持默认即可
> （超时 15 秒、校验开启）。内网自签 https 证书的实例暂时用不了自动开通，
> 请继续用手工填 Key。

## 三点五、打开开关之后，**已经在册的人**会怎样

这一节容易被漏掉，但它决定了你打开开关之后要不要再动手。四种人，行为各不相同
（下面这四条都在本机实测过）：

| 这个人现在是什么情况 | 打开开关之后会怎样 |
|---|---|
| 从来没有过网关记录（自动开通上线之前建的号，**包括管理员你自己**） | 后台会自动给他补一行并开通，你不用管 |
| 在开关**关着**的时候建的号（界面上标着「需要手工处理」） | **不会**自动补开通。要让系统去办，得到「成员账号」页对他点一次「重新开通」 |
| 已经被你手工填过 Key（能正常生图） | 完全不动他。想改成自动，得先点「清除」把手工那把 Key 删掉，再点「重新开通」 |
| 曾经自动开通成功、密码已按默认设置清空 | 不能再自动开一次（见第七节），只能手工填 Key。点「重新开通」会当场告诉你这一点 |

> ⚠️ **管理员自己也会被开一个账号**，这一条请特别注意。
> 在「每人一把 Key（各花各的）」模式下，一旦管理员本人有了自己的网关账号，
> **他自己的生图、以及所有 ERP 对外接口的任务（那些 API Key 都归 admin）
> 就会开始从他这个新账号的额度走，而不是「生图服务」里那把全局 Key。**
> 这是「谁的任务花谁的 Key」这条规则的正常结果，不是 bug，但你要知道，
> 否则会看到「全局 Key 的余额不动了，另一个账号在扣」而查不出原因。
> 不想这样的话，就把管理员那一行手工填成全局那把 Key（在「成员账号」页对 admin 那一行操作）。

## 四、怎么测（点一个按钮，不建号、不发 Key、不花钱）

同一节最下面有个**「测试能不能自动开通」**按钮。

- 有未保存的改动时它会拒绝执行并提示「请先保存当前更改」——它测的永远是**已保存**的配置。
- 它**全程只读**：只去网关那边看几个设置，不建账号、不发 Key、不代任何人登录、不碰余额。
- 结果是一盏三色灯 + 一段结论 +「要你去做的事」+ 逐项明细。

三色灯怎么读：

| 灯 | 意思 | 你要做什么 |
|---|---|---|
| 🟢 可以自动开通 | 前提条件都满足 | 没事了。但**别忘了确认总开关是打开的**——绿灯只说明网关那边行，不代表你已经打开了自动开通（这种情况页面上会单独提示） |
| 🟡 能用，但有几处要注意 | 能开通，但有隐患（例如网关开着两步验证，成员随时可能自己给自己开上，把自己踢出自动开通） | 看「要你去做的事」那一段，能处理就处理 |
| 🔴 现在开不通，需要先处理 | 前提条件不满足 | 按提示处理。**系统会当场把「自动给新成员开通」自动关掉**（免得所有新人一直白撞墙），处理完回来点「我已处理，恢复自动开通」 |

**关于「未验证」（灰色标签）**：有两项天生就可能查不了——

- 「已发 Key 可用性」：库里还没有任何一个开通成功的成员时，没有 Key 可以抽查。
- 「建 Key 路由」：手上没有现成的登录令牌时无从验证，
  而**系统绝不会为了点亮这一项去真的登录一次**（真登录会在网关那边留一条登录记录、
  占用限流额度，一个「测试」按钮不该有这些后果）。

**「未验证」就是「这次没查」，不是「查过了没问题」。** 界面上会照实显示成灰色的「未验证」，
不会画成绿灯。第一次配置时看到这两项是灰的，属于正常。

## 五、上线前必须做的两件事

这一节请**务必**做完再让同事们用。原因是：这套功能是照着网关的源码默认值写的，
而**源码默认值不等于你那台机器上的实际取值**——你那台是别人装好的、可能改过设置。

**第 1 件：点一次「测试能不能自动开通」，把「实例真实配置」这一项读一遍。**

自检会把从**你那台机器上真实读回来的值**摆出来（不是源码默认值）：
后台模式开没开、三个人机验证开没开、两步验证开没开、网关版本号、合规承诺版本号，
以及（库里已经有开通成功的人时）那个远端账号的实际并发数、限速、绑的分组。

要点：

- **后台模式**和**三个人机验证**只要有一个是「开」，自动开通就一定不通——
  系统没法代成员登录网关，也就发不出 Key。请到网关后台关掉，或者干脆不用自动开通。
- **两步验证**开着是黄灯：不是立刻不通，但成员随时可能自己给自己开上，
  一旦开了，那个人就永久开不通了，只能手工发 Key。
- **两个版本号请抄下来**（网关版本 / 合规承诺版本）。以后升级网关时用得上，见第九节。

**第 2 件：拿一个测试账号，真的生成一张图。**

自检里那一步「冒烟」只能证明网关**愿意受理**这把 Key（HTTP 通了），
**证明不了真能出图**。已知的坑是：网关那边如果给这个账号的并发数写成了 0，
Key 看着一切正常，实际一张图都发不出来。系统建号时已经显式要求并发 5，
但那台实例会不会照做，只有真出一张图才知道。

做法：建一个测试成员 → 等它显示「已开通」→ 用这个账号登录 → 传张图点生成 → 出图 → 停用这个测试账号。

## 六、它会失败，而且有一小撮人会**永久**卡住

**这是设计的一部分，不是 bug。** 原因是自动开通中间有一步是「系统代替这个成员登录网关」，
而这一步依赖五件事同时成立：网关没开后台模式、没开人机验证、没开会话绑定、
**这个成员自己没开两步验证**、**这个成员自己没改过网关密码**。
后两件是成员自己就能触发的，系统既拦不住也修不好。

所以现实的预期是：**绝大多数人一次就通，少数人怎么试都不通。**

### 卡住了怎么办

打开「成员账号」页，卡住的行会标成 **🟡 需要手工处理**，下面写着原因、已经自动试过几次、
下次什么时候再试。这一行有两个按钮：

- **「重新开通」**——把这个人重新排进队，后台通常一分钟内跑完（点完页面不会自己变，
  点列表上方的「刷新」看结果）。适合「网关刚才在重启」这类临时问题。
- **「改用手工填 Key」**——**这是终点，也是永远可用的那条路。**
  你去网关后台给这个人开一把 Key，整串粘进来，保存。**存进去立刻就能用**，
  不用再等自动开通，后台也不会再去动这一行。

> 别在「重新开通」上反复点。可以自动重试的那几种失败，系统自己会按
> 1 分钟 → 5 分钟 → 30 分钟 → 2 小时 → 12 小时的节奏重试（大约覆盖 15 个小时，
> 足够熬过一次夜间维护）；不能自动重试的那几种，点一百次也是同一个结果。
> 连续失败到「最多自动重试几次」那个数之后，这一行会自动转成「等你手工发 Key」。

### 各种失败原因对照表

界面上显示的是人话，不会出现代号。下表里的**代号**只在服务日志里出现，
留给排查时 grep 用。

| 界面上大意是 | 代号 | 会自动重试吗 | 你该做什么 |
|---|---|---|---|
| 连不上网关（超时或网络不通） | `E_NETWORK` | 会 | 等着。多半是 NAS 或网关在重启 |
| 网关内部出错了 | `E_SERVER` | 会 | 等着 |
| 被网关限流了 | `E_RATE_LIMITED` | 会 | 等着 |
| 幂等存储忙 | `E_IDEMPOTENCY_BUSY` | 会 | 等着 |
| 网关不认这个成员的 Key | `E_KEY_REJECTED` | 会 | 若一直不好：那把 Key 多半在网关后台被删/被禁用了，改用手工填 Key |
| 排队等登录名额超时 | `E_LOGIN_BUSY` | 会（且**不计入失败次数**） | 等着。同时开通的人多时的正常现象 |
| 这个成员开了两步验证 | `E_LOGIN_2FA` | **不会** | 手工填 Key。系统拿不到动态码，网关也没有替他解绑的接口 |
| 这个成员自己改过网关密码 | `E_PASSWORD_MISMATCH` | **不会** | 手工填 Key |
| 网关开着「后台模式」 | `E_BACKEND_MODE` | **不会**，且会**暂停全站自动开通** | 去网关后台关掉它，回来点「我已处理，恢复自动开通」 |
| 网关开着人机验证 | `E_CAPTCHA_ON` | **不会**，且会**暂停全站自动开通** | 同上 |
| 网关要求先签合规承诺 | `E_COMPLIANCE` | **不会**，且会**暂停全站自动开通** | 登录网关后台重新签一次合规承诺，回来点「我已处理，恢复自动开通」 |
| 管理员 Key 不对或没权限 | `E_ADMIN_AUTH` | **不会**，且会**暂停全站自动开通** | 回「系统设置」重新填一次管理员 Key |
| 找不到网关的接口地址 | `E_ROUTE_MISSING` | **不会** | 地址填错了，或网关升级挪了位置。见第九节 |
| 这把 Key 没绑到任何分组 | `E_NO_GROUP` | **不会** | 检查「目标分组 id」填得对不对，改完点「重新开通」 |
| 网关不允许这个成员用这个分组 | `E_GROUP_DENIED` | **不会** | 同上 |
| 建 Key 次数被网关限制了 | `E_KEY_RATE_LIMITED` | **不会**（**故意的**） | 过一小时再点「重新开通」，着急就手工填。系统撞上这个会**立刻停手**——继续换名字重试会把这个成员在网关那边锁死一整个小时 |
| 建号参数被网关的策略拒了 | `E_BAD_REQUEST` | **不会** | 多半是「成员邮箱后缀」不被网关接受，换一个 |
| 网关的响应不是预期格式 | `E_PROTOCOL` | **不会** | 地址填错了，或者网关升级了。见第九节 |
| 系统这边配置没填齐 | `E_LOCAL_CONFIG` | 配齐了自动继续（**不计入失败次数**） | 回设置页补齐地址 / 管理员 Key / 分组 id |
| 系统这边没有这个成员的网关密码了 | `E_LOCAL_NO_PASSWORD` | **不会** | 手工填 Key（这是第七节说的那个代价） |
| 网关说邮箱已存在，但又查不到 | `E_LOCAL_EMAIL_GHOST` | **不会** | 去网关后台看一眼这个邮箱，或直接手工填 Key |
| Key 的名字被别人占了 | `E_LOCAL_KEY_SQUATTED` | **不会** | 手工填 Key |
| 失败次数打满，已转手工 | `E_LOCAL_MAX_ATTEMPTS` | **不会** | 手工填 Key，或修好根因后点「重新开通」 |
| 自动开通被暂停了 | `E_LOCAL_PAUSED` | 解除后自动继续（**不计入失败次数**） | 见下一节 |

### 「全站暂停」是怎么回事

有几种失败（后台模式、人机验证、合规未签、管理员 Key 失效、接口找不到）
意味着**每一个人**都会以同样的方式失败。这时系统会**主动暂停整个自动开通**，
并在设置页顶部挂一条红条写清原因。

这么做的理由：不暂停的话，后台会挨个把全站成员刷到失败上限、集体降级成「等人工发 Key」，
而这本来只是**改一个开关就能修好**的问题。

处理完之后，点红条下面的**「我已处理，恢复自动开通」**。它会同时解除暂停并把总开关重新打开
（暂停时这两处是一起关掉的，只解一处的表现是「点了没用，重启又暂停」）。

> 暂停是记在内存里的，重启服务也会解除。但**根因没修好的话，下一轮又会暂停**。

## 七、为什么默认**不**保管成员的网关密码

开通过程中，系统会给这个成员在网关那边生成一个随机密码（43 位随机字符，
不是从任何人的登录密码推出来的），加密存进数据库。

**开通成功那一刻，这个密码立刻被清空**——这是默认行为（「保管成员在网关的登录密码」默认关闭）。

为什么这样更安全：拿回一把**已经发出去的** Key 只需要管理员 Key 就够了，
**只有「新建 Key」那一次**才需要成员的密码。所以开通成功之后留着它没有用处，
删掉之后 DesignKit 长期保管的就只是**一堆 Key**，而不是**一堆能登进网关的账号密码**——
万一数据库泄露，前者能被网关后台一键作废，后者要一个个去改密码。

**代价（必须知道）**：这一行以后**不能再自动重建 Key** 了。
哪天这个成员的 Key 在网关后台被删了，系统自己办不了，只能你手工填一把。
界面上会写「系统这边已经没有这个成员在网关的登录凭据了」。

想留着的话，把那个开关打开——但请清楚你换到了什么：换来的是「将来能自动重建 Key」，
付出的是「系统里长期躺着一堆能登录网关的凭据」。

> 不管开还是关，**界面上永远看不到这个密码**，任何接口都不返回它。
> 这不是「藏起来了」，是系统里压根没有「查看密码」这个功能。
> 同样地，成员的 Key 在界面上也一个字都看不到（连末 4 位都没有）。

---

## 八、成员那边看到的是什么

**什么都看不到。** 成员不知道自己在网关那边有个账号，界面上也不会出现
「网关」「Sub2API」这类词。

他能看到的只有「我的」（我的账户）页里的**「生图额度」**一行，
两种取值：「可以生图」或者「暂时不能生图 + 一句该找谁的话」
（通常是「你的账号还没有开通生图额度，请联系管理员在『成员账号』页配置」）。

所以还没开通完的那几分钟里，成员点生成会被拦住并看到这句话。
**如果他着急**，最快的解法永远是你去手工给他填一把 Key（存进去立刻生效）。

> 账单口径上要说清的一句话（PRODUCT.md 里也写了）：
> **每个成员的生图额度是系统在图片网关上为他单独开的账号，用量单独计算。**
> 这既是诚实，也是将来对账有争议时的依据。

## 九、升级网关（Sub2API）之后要复核什么

这套功能依赖的很多东西是网关的**实现细节而不是公开契约**——
接口路径、409 的含义、Key 是否能原样读回、合规版本号常量，等等。
**网关升上去一个版本，自动开通可能一夜之间全断**（表现是所有新成员都开不通，
老成员照常生图不受影响）。

升级之后请按顺序做这三件事：

1. **点一次「测试能不能自动开通」**，对比第五节抄下来的两个版本号。
   网关版本变了就说明要重新验一遍；合规承诺版本变了说明**之前签的已经作废**，
   得登录网关后台重新签一次。
2. **跑一遍自动开通的回归测试**（见 `tests/README.md`，命令是
   `.venv/bin/python -m unittest discover -s tests -p 'test_provision*.py'`）。
   这组测试对着一台**假网关**跑，不联网、不花钱，验的是「我们的代码有没有按契约写」。
   它挡不住网关自己改了契约——那要靠第 1 步和第 3 步。
3. **建一个测试成员，真的走一遍开通并出一张图**（同第五节第 2 件事）。

给开发者的额外一条：如果网关某个版本给管理端加上了「替用户签发 Key」的接口，
那么整条「保管密码 + 代替用户登录」的链路就该立刻废弃（更简单也更安全）。
在网关源码目录里用这两条命令看一眼：

```bash
grep -rn "GenerateTokenPair\|GenerateToken(" backend/internal/handler/
# ↑ 看这些函数是否出现在 admin 目录下

# 再看 routes/admin.go 里的 api-keys 那一组有没有多出 POST
```

## 十、系统在网关那边到底做了什么、以及**绝不会**做什么

**会做的（全部三步，都是可以安全重跑的）**：

1. 用管理员 Key 建一个账号（邮箱是 `dk<编号>@<你填的后缀>`，密码随机）。
   重跑时如果网关说「这个邮箱已存在」，系统会**按完整邮箱反查并逐字比对**再认领，
   绝不会认错人——认错人的后果是把 Key 建到别人账号上，而且毫无报错。
2. 代替这个成员登录一次，拿一张临时令牌（**只在内存里，绝不落库**），用它建一把 Key。
   Key 的名字是按成员编号算出来的固定值，所以重跑要么建成、要么撞上「已存在」再原样读回，
   **绝不会给同一个人发出两把 Key**。
3. 用刚拿到的这把 Key 打一次网关的只读接口做冒烟。**只有这一步通过才算开通成功。**

**绝不会做的**：

- **不删任何东西**：不删远端账号、不删 Key。停用一个成员时，网关那边的账号和 Key 原样保留。
- **不碰任何余额**：不充值、不扣款、不生成兑换码。额度请在网关后台统一配置
  （按分组订阅或初始余额）。这样从结构上就不存在「重复扣钱」这类风险。
- **不把密码或 Key 写进日志**：日志里最多出现 Key 的末 4 位。
  （有一项专门的自动化测试装了个假日志处理器，把整条链路的全量日志抓下来搜一遍，
  确认密码、完整 Key、管理员 Key、登录令牌一个都不出现。）

## 十一、给开发者的速查

- **状态机**：`backend/app/services/provisioning.py`（七个状态：
  `pending` → `user_created` → `key_issued` → `active`，外加 `failed` / `manual` / `disabled`）。
  文件头有完整的状态语义说明。
- **HTTP 客户端**：`backend/app/services/sub2api.py`（含 24 个失败分类码与人话对照表 `ERROR_CODES`、
  五项只读探针 `run_probes`）。
- **触发时机**：建成员时 `routers/users.py` 只**登记一行**（零网络请求，失败也不影响建号）；
  真正的开通由 `services/scheduler.py` 的后台线程做，每 60 秒一轮，
  每轮最多推进 20 个人；已开通的人每 10 分钟同步一次余额（每轮最多 25 个）。
- **设置项**（都在 `config.py` 的 `RUNTIME_DEFAULTS` 里，**都不读环境变量**）：
  `sub2api_auto_provision` / `sub2api_base_url` / `sub2api_admin_key`（打码，且**连末 4 位都不给**）/
  `sub2api_group_id` / `sub2api_email_domain` / `sub2api_keep_password` /
  `sub2api_max_attempts` / `sub2api_timeout` / `sub2api_verify_tls`。
- **接口**：`POST /api/web/settings/test_provisioning`（自检，永远返回 200，成败看 `level`）、
  `GET /api/web/settings/provisioning`（面板概览，零网络请求）、
  `POST /api/web/settings/provisioning/resume`（解除暂停）、
  `POST /api/web/users/{id}/gateway/provision`（重新开通，只排队不等结果）。
- **测试**：`tests/test_provisioning.py`（状态机 54 项）、
  `tests/test_provision_regression.py`（端到端 36 项）、
  `tests/test_provision_schedule.py`（触发时机 27 项），共用假网关 `tests/fake_sub2api.py`。
- **尚未接线**：`gateway_shared_fallback`（「故障期让所有人临时共用一把 Key」的救命开关）
  这个设置键已经存在，但 `settings_service.resolve_for_user` 还没读它，
  **打开不会有任何效果**，界面上也没有入口。故障期的兜底手段目前只有「手工填 Key」。
