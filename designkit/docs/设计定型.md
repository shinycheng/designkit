# designkit 设计定型（v2，2026-08-12）

v1 草案经 9 个 agent 对抗性评审，查出 5 处致命错误，这是修正版。
**v1 的错法都记在各节的「⚠v1 错在哪」里——那是最贵的知识，别删。**

依据见 `CLAUDE.md` 第二·五节。标 **⚠未知** 的是代码里查不到、必须实测的。

## 一、出图请求怎么发出去

**在进程内构造合成 `gin.Context`，重入 `h.OpenAIGateway.Images()`。**
`h.OpenAIGateway` 是 `handler.Handlers` 的导出字段（`handler.go:59`），直接传进来即可。

### 1.1 合成 context 的六步（照抄 `image_task_handler.go:260-278`，一步都不能漏）

```
1. ctx = context.WithoutCancel(原始ctx)   ← 漏了：运营一关页面整批 canceled，图已出、钱已扣
2. ctx, cancel = context.WithTimeout(ctx, 单张超时)
3. req = 新建 http.Request（不是 Clone 入站请求，我们没有入站 multipart）
4. 换 Body / GetBody / ContentLength
5. taskCtx = c.Copy()                      ← 每个 item 造一份，共用会互相覆盖账号选择
6. taskCtx.Writer = recorder.Writer        ← 漏了：往已归还对象池的 Writer 上写，高并发串包或 panic
```

**每个 item 一份独立的 `Request` 和 `recorder`。** 单测断言 `taskCtx.Writer != 原始 Writer`。

### 1.2 multipart 要自己拼（上游没得抄）

`AsyncImageHandler` **根本没有伪造 multipart**——它 Clone 入站请求、原样透传客户端送来的 body。
我们的图字节来自对象存储、提示词来自数据库，必须自己 `multipart.NewWriter`：

- 文件字段名**必须是 `image`**，否则报 `image file is required`
- 另加 `prompt` / `model` / `size` 三个 `WriteField`
- `Content-Type` 用 `w.FormDataContentType()`
- `ContentLength` 和 `GetBody` 都要设
- **`URL.Path` 必须含 `/images/edits` 字面量**——上游是从路径 `strings.Contains` 出端点的
- **显式剔除 `session_id` / `conversation_id` / `x-session-id`**，否则一批 50 张全粘到同一个上游
  账号，撞上 `accounts.concurrency` 默认 3，批量退化成三张三张串行

### 1.3 ⚠必须覆写 request id，否则一单 N 张只扣 1 张的钱

**这是 v1 最贵的一个错。** 上游算计费幂等键时**优先取 ctx 里的 `ClientRequestID`**
（`gateway_usage_billing.go:214-217`），而 `RequestLogger` 是全局中间件
（`router.go:59`），每个入站 HTTP 请求注一个 id；合成 context 继承全部 ctx value。
于是一次 `POST /jobs` 展开的 N 张图**共用同一个 id** →
幂等表唯一键 `(request_id, api_key_id)` → 第 2 张起 `applied=false` **静默不扣**。

更糟：multipart 的计费指纹只取 `StickySessionSeed`，**seed 里不含图片字节**，
所以「图1×词1」和「图2×词1」指纹完全相同。

→ **在合成请求的 `Request context` 上无条件覆写**（不是「没有才设」）
`ctxkey.ClientRequestID` **和** `ctxkey.RequestID`，值为该 attempt 独有的 id（见第四节）。

### 1.4 结果读取（也照抄）

先 `bytes.TrimSpace`（非流式生图会周期写 `" \n"` keepalive）→
`recorder.Code == 0` 视作 200 → 再 `json.Valid`。
每个出图 goroutine 第一行 `defer recover`，recover 后把该 item 置 failed 并继续跑其余的。

对外暴露 `uid`（26 位 ULID），不暴露自增主键。

### 2.5 `designkit_jobs` — 一次提交

基础列：`id` / `uid`(UNIQUE) / `user_id` / **`api_key_id` BIGINT NOT NULL** /
`origin`(`web`|`erp`) / `name` / `status` / `ratio` / `model` /
`item_count` / `success_count` / `fail_count` / `cancelled_count` /
`idempotency_key` VARCHAR(128) / `callback_url` / `expires_at`（预留） /
`created_at` / `updated_at` / `started_at` / `finished_at` / `settled_at` /
`user_deleted_at` / **`heartbeat_at`** / **`cancel_requested_at`** / **`revision` INT**

金额列：`estimated_cost` / `actual_cost`
定价快照列（照抄上游 `batch_image_public.go:266-282`）：
`base_unit_price` / `group_rate_multiplier` / `account_rate_multiplier` /
`billing_mode` / `pricing_tier` / `price_source` / `pricing_snapshot_version`

索引：`uid` UNIQUE、`(user_id, created_at DESC)`、`status`、
`(user_id, idempotency_key)` **普通部分索引，不是 UNIQUE**。

> **⚠ 别写 `ON CONFLICT (user_id, idempotency_key)`——会在运行时报 42P10。**
> 幂等由上游协调器负责，scope 揉进用户：`"designkit.jobs.create:user:" + userID`（见 3.2）。
> 3.2 说过「协调器和唯一索引二选一，不能都要」，迁移选了协调器这一边。
> `9001_designkit_init.sql` 已经定稿且**永不可改**，所以以迁移为准。

> **⚠v1 错在哪**：v1 写 `api_key_id`「浏览器为 NULL」。**网页端会 100% 走不通**——
> `Images()` 第一件事就是 `GetAPIKeyFromContext`，取不到直接 401
> （`openai_images.go:29-33`）；`usage_logs.api_key_id` 还是 NOT NULL + 外键。
> 硬塞假 Key 的后果正是 `CLAUDE.md` B1：钱扣了、账单写不进、只打一行日志。
>
> **正解**：每个运营用户首次进工作台时，服务端自动给他建一把**内部专用 Key**
> （放 designkit 专属分组、界面不暴露）。`APIKeyService.Create(ctx, userID, req)`
> 签名带 `userID` 且函数体内**没有管理员校验**（`api_key_service.go:461-466`），
> 服务端可以为任意用户建——「admin 不能替用户签发」那条限制只在网页 UI 层成立。
> 附带好处：ERP 和运营天然落不同分组，`CLAUDE.md` B7 说的「按分组区分 RPM」直接可用。
> 建 Key 失败时界面显示中文「账号还没开通出图权限，请联系管理员」。

**状态机**（白名单函数，不许随手 UPDATE status）：

```
created → holding → running → settling → ┬→ succeeded
                                          ├→ partially_failed
                                          └→ failed
running → (cancel_requested) → 在途清空 → settling → cancelled
{succeeded|partially_failed} → running     ← 仅 retry 可触发，同时 revision+1
任意 → failed（冻结失败、僵尸回收）
```

**禁止**「running 且存在在途 item → cancelled」的直接迁移（见第六节）。

`created_at` / `updated_at` / `started_at` / `finished_at`

### 2.7 `designkit_images` — 结果图

`id` / `uid`(UNIQUE) / `job_id` / `item_id` / `attempt` / `image_index` /
`is_current` / `object_key` / `content_type` / `byte_size` /
`width` / `height` / `billing_tier` / `created_at` / `deleted_at` / `expires_at`

索引：`uid` UNIQUE、`(item_id, attempt, image_index)`（**普通索引，不是唯一**）、
`(item_id, image_index)` partial UNIQUE `WHERE is_current AND deleted_at IS NULL`。

> 唯一键里**带 `image_index`**（比原稿多一列）：万一网关一次返回 2 张图，
> 单列唯一键会让第二张插不进去——**钱花了、图丢了**。`n=1` 时两种写法行为一致。
> 写入用 `ON CONFLICT (item_id, image_index) WHERE is_current AND deleted_at IS NULL`。

`object_key` 格式定死：
`designkit/<YYYY>/<MM>/<DD>/<job_uid>-<seq>-<attempt>-<image_index>.png`
（相对 bucket、含 prefix、不含域名不含签名）。**URL 一律运行时生成，绝不入库。**

> `image_index` 是防御性的：⚠未知——自建网关一次会不会返回多张图。先加着，成本为零。

### 2.8 `designkit_holds` — 我们自己的冻结账（见第五节）

`id` / `job_id` / `user_id` / `amount` / `status`(`open`|`settled`|`released`) /
`created_at` / `updated_at`

索引：`(user_id, status)`、`job_id` UNIQUE。

### 2.9 `designkit_billing_alerts` — 实际额超出预估的告警

`id` / `job_id` / `estimated` / `actual` / `ratio_over` / `level` / `created_at`

### 2.9b `designkit_quota_requests` — 申请额度（决策 19）

`id` / `user_id` / `note`（运营填的说明，可空） / `status`(`pending`|`handled`|`rejected`) /
`handled_by` / `handled_at` / `created_at`

索引：`(status, created_at)`、`(user_id)` partial UNIQUE `WHERE status='pending'`
（同一个人只能有一条待处理，防止连点刷屏）。

### 2.10 `designkit_sync_runs` — 灵感库同步

`id` / `kind`(`manual`|`auto`) / `status` / `started_at` / `finished_at` /
`fetched` / `inserted` / `updated` / `skipped` / `error`

**手动和自动共用同一把锁**，用 PostgreSQL advisory lock（`pg_try_advisory_lock`），
不要用应用内 mutex——多副本部署时应用内锁失效。
（老系统曾各用一把，并发把 1.4 万条写重复。）

### 2.11 `designkit_settings`

`key` VARCHAR(64) PK / `value` JSONB / `updated_at`。
存比例清单、单次批量上限、单张超时、`max_dimension`、并发上限。**不碰上游 `settings` 表。**

### 3.5 用出好的图接着做下一轮（2026-08-14 上线）

```
POST /assets/from-image/:uid      浏览器和 ERP 组都挂
→ 201  assetDTO（跟 POST /assets 同一个形状）
```

把一张**已经出好的结果图**变成一条新的商品图，调用方拿到的是**商品图编号**，
接着就能塞进 `POST /jobs` 的 `asset_uids`。

⚠ 路径放在 `/assets` 下而不是 `/images` 下：**产出物是一条 asset**。
挂成 `/images/:uid/continue` 会让人以为返回的是图片。

⚠ **图片字节不经过浏览器**：服务端直接从存储里复制。
前端本来也能做（取图 → 构造 File → 调 `POST /assets`），但那是下行 2MB + 上行 2MB，
远程使用时点一次要等好几秒还吃上行带宽。

⚠ **重复调不会存重复的图**：`AssetService.UploadAsset` 按 sha256 去重，
同一张图拿到的是同一条 asset 记录，磁盘上只有一份。
前端也做了一层去重 —— 不判的话商品图列表里会出现两条一模一样的，
而**张数是按条数算的，直接多花一份钱**。

⚠ 实现上**只在 handler 层组合**（`images.OpenImageContent` + `assets.CreateAsset`），
没有新写 service：两个端口本来就都在 handler 里，再包一层没有收益。
结果图服务缺席时**整条路由不挂**（跟别处一个规矩，宁可 404）。

### 3.4 AI 挑提示词（2026-08-14 上线）

```
POST /prompts/suggest        浏览器和 ERP 组都挂
{
  "asset_uid":        "01K...",        // 必填，主商品图
  "extra_asset_uids": ["01K...", ...], // 可空，其余商品图（连主图封顶 3 张）
  "category_slug":    "",              // 空串 = 全部，由后端让模型自己判
  "features":         "米白色针织开衫，秋冬新品"   // 可空，运营填的商品特点
}
→ 200
{
  "prompt":   "合成出来的最终提示词全文",
  "category": { "slug": "...", "name": "电商主图" },
  "candidates": [ { "uid": "...", "title": "..." } ],   // 参考过的 5 条
  "note":     ""                                        // 可空，给运营的中文说明
}
```

⚠ **服务缺席时这条路由整个不挂**，让它自然 404。前端靠「裸 404（响应体里没有
`DK_` 前缀的错误码）」区分「功能没上线」和「业务错误」——挂上去再返回一个
`DK_` 码的话，第一种情况会被显示成「再点一次试试」，而运营会一直点、永远不成功。

⚠ **不要求 `Idempotency-Key`**：它不建任何东西、不冻结额度，重复提交最坏是
多花几毛钱对话费。加一道幂等只会让前端多一件必须做对的事。

⚠ **这个接口要跑 1~2 分钟**（四趟对话串行）。前端为它单独把超时放宽到 **240 秒**
（axios 单例默认 30 秒）。后端单趟超时 35 秒，四趟加起来必须明显小于 240，
否则前端先报超时、后端还在算还在花钱。

**金额一律美元**（决策 18）。接口里带 `currency` 字段固定 `USD`，
界面渲染 `$`，**文案里不许出现「元」**。

### 3.1 错误格式（对 ERP 只承诺一种）

上游同一个端点会吐出**三种互不兼容**的错误 JSON
（`middleware.go:63-81` 的 `{"code":字符串}`、`response.go:15-21` 的 `{"code":整数}`、
`batch_image_handler.go:290-315` 的 `{"error":{...}}`）。ERP 用强类型语言反序列化
会在 Key 过期那天偶发解析异常，**发布后改不了**。

在 `/v1/designkit` 组最前面挂一个自写的 response-rewriter 中间件统一改写成：

```json
{"error":{"type":"invalid_request_error|authentication_error|rate_limit_error|api_error",
          "error_code":"UPPER_SNAKE","message":"人话","request_id":"..."}}
```

字段名用 `error_code` **不用 `code`**（原因见 3.2）。每个响应回 `X-Designkit-Request-Id` 头。
错误码全集列进 ERP 文档。

### 3.2 幂等

上游协调器的唯一键是 `(Scope, keyHash)`，**不含用户**——两个用户用同一个 key 会撞成 409。
`ObserveOnly` 默认 `true`，**不带 key 直接放行执行**（ERP 超时重发 = 重复下单重复扣钱）。
key 规格 ≤128 且只允许 33-126 可见 ASCII。存库前会把名为 `code` 的字段脱敏成 `***`。

**选定**：复用上游协调器，但把用户揉进 scope：
`opts.Scope = "designkit.jobs.create:user:" + userID`，
同时**删掉** `designkit_jobs` 上的 `(user_id, idempotency_key)` 唯一索引（二选一，不能都要）。

写进 ERP 文档并加契约测试：
- 缺 `Idempotency-Key` 由**我们的 handler 直接 400**，不依赖 `ObserveOnly`
- **浏览器端也必须带**（打开确认弹窗时生成 UUID 存住），否则运营手滑双击 = 两个 job 两份钱
- 同 key 不同 body → 409；同 key 同 body → 返回原结果；窗口 24 小时
- `POST /jobs` 成功响应只返小对象（`id`/`status`/`item_count`/`estimated_cost`/
  `currency`/`created_at`），**绝不内联 items 数组**（断言 <8KB）；
  对外 JSON **禁止出现名为 `code` 的字段**

### 3.3 分页

ERP 拉历史用**游标分页**（`created_at` + `id` 复合游标），不用 offset——
offset 在持续写入时会漏数据。

## 四、request_id 格式

只有**一种**：

| | 值 | 长度 |
|---|---|---|
| 我们生成 | `dki:<job_uid>:<seq4位>:<attempt2位>` | 38 |
| 实际落进 `usage_logs` | `client:` + 上面 | 45 |

规则写死：**同一 `(seq, attempt)` 无论重投几次都用同一个 id**（幂等）；
**`attempt` +1 就换新 id**（该扣）。
`designkit_job_items.billing_request_id` 存**带 `client:` 前缀的完整值**，否则反查 `usage_logs` 一条查不到。

> **⚠v1 错在哪**：v1 定了 `dkh:`/`dkc:`/`dkr:`/`dki:` 四个前缀。
> 前三个随 (D) 方案整体删除；`dki:` 那条错在两点：
> ① **没有 attempt 维度**——重试沿用同一个 id，上游判成重复，图重出了、成本产生了，
> 我们**一分钱不扣**；
> ② 「≤48 是硬约束」的依据是错的。真实上限是 `usage_logs.request_id` 的
> `VARCHAR(64)`，而我们给的不是最终落库值（上游拼 `client:` 7 字节），
> 所以可用上限是 **57**，48 只是安全余量。
> 单测断言 `len("client:" + id) <= 64`，并遍历 attempt 维度。

## 五、钱的流程（方案 D）

> **⚠v1 错在哪（最贵的一处）**：v1 想复用上游的 Reserve/Capture/Release 做冻结。
> **四条全部验实、四条全部致命**：
> 1. 上游 `Reserve` **真的从 `balance` 里划钱**（`usage_billing_repo.go:275-291`）；
> 2. 上游每张图出图前的准入判据就是 `balance <= 0`
>    （`api_key_auth.go:393-395`、`billing_cache_service.go:871-877`、调用点 `openai_images.go:136`）
>    → 余额 100、冻结 100 → **本批次每一张都被判余额不足，一张也出不来**；
> 3. `Release` 的防幻影守卫把 hold 键**硬编码成 `batch_image_hold:` 前缀**
>    （`usage_billing_repo.go:340`）→ 我们用 `dkh:` 冻结会查不到，
>    **打一行日志、返回 error 为 nil，钱永久卡在 `frozen_balance`，无任何报错**；
> 4. `Capture` 在 `actual - hold > 1e-8` 时直接返错回滚（`:306-308`），
>    而 `CLAUDE.md` B3 已实测档位会向上漂，`actual > hold` 是**常态**。
>
> 方案 C（让上游跳过计费）也出局：全链路**没有任何 per-request 的跳过开关**，
> 唯一 bypass 是全局 `RunModeSimple`。
>
> **上游 `batch_image` 的 hold/capture 之所以不双扣，是因为它绕开网关直连 provider**
> （`batch_image_provider_vertex.go` 直接 http 调用，全程不经 `Images()`/`RecordUsage`）。
> 我们重入 `Images()`，前提正好相反，**不可照抄**。

**方案 D：完全不碰上游的冻结接口，`users.balance` 全程只由上游扣一次。**

```
1. POST /jobs（必须带 Idempotency-Key）
2. 一个事务里：
     SELECT balance FROM users WHERE id=? FOR UPDATE
     可用额 = balance - SUM(designkit_holds.amount WHERE user_id=? AND status='open')
     可用额 < 预估 → 422「还差 X」，事务回滚，什么都没建
     INSERT designkit_jobs (status='created', 定价快照) ON CONFLICT DO NOTHING RETURNING
       ↑ 没返回行 = 幂等重试，直接返已有 job
     INSERT designkit_job_items
     INSERT designkit_holds (status='open')
   提交 → status = holding → running
3. worker 领取 item（见第六节的 SQL），逐张出图，自己节流
4. 每张走合成 gin.Context 重入 Images()；上游扣一次钱、写一条 usage_logs
5. 每张计费落地后：按张递减该 job 的 open 冻结额，回填 items.billed_cost
6. 所有 item 到终态 → job 置 settling
7. 结算 worker 按 items.billing_request_id 去 SUM(usage_logs.actual_cost)；
   命中条数 < 成功张数就指数退避重试（上限 5 次）；全部命中才置终态 + settled_at
8. 剩余 open 冻结额置 released
```

**那条 `FOR UPDATE` 就是全部的并发防护**——它把 `CLAUDE.md` B4 说的「50 张全部放行」
窗口关死了，而且上游看到的 `balance` 始终是真实可用余额，不会自我拒绝。

**第 7 步不许写 `assert actual - hold <= 1e-8`**（那是 C 方案的断言）。
钱已经被上游扣走了，报错只会让 job 卡死。改成分级告警：
`actual > estimated × 1.2` 记一条 `designkit_billing_alerts`，`× 2` 额外告警。

**结算不能在最后一张图返回时立刻做**——上游写 `usage_logs` 是**异步**的
（丢进 worker 池就返回，`openai_gateway_handler.go:2432-2446`），
立刻汇总很可能少算甚至全算 0。这就是 `settling` 状态存在的理由。

**金额一律 `SUM(items.billed_cost)`，禁止用 `success_count × 单价`**——
同一批 10 张可能落不同计费档、单价不同（`CLAUDE.md` B3）。

**计数列一律 `SET success_count = success_count + 1` 原子自增**，绝不读回来再写。

**终态判定和回调触发合并成一条带守卫的 UPDATE**，只有 `RowsAffected=1` 的 worker
去结算和发回调（否则 5 个 worker 都以为自己是最后一张，**回调发 5 次**）：

```sql
UPDATE designkit_jobs SET status=?, finished_at=NOW()
WHERE id=? AND finished_at IS NULL
  AND success_count + fail_count + cancelled_count = item_count
RETURNING id
```

### 5.1 崩溃恢复（v1 完全没有）

- `designkit_jobs.heartbeat_at`，worker 每 30 秒续
- 收到 SIGTERM 停止领新 item（上游优雅关闭只给 5 秒，`main.go:181-186`，
  一张图要 20 秒——后台 goroutine 根本不在等待范围内）
- 照抄上游 `BatchImageBillingRecoveryService` 的形态（`batch_image_billing_recovery.go`）

**巡检一共扫三样**（2026-08-13 补齐，`repository.ReapStaleJobs` 一个事务三段，
每分钟一轮）。判据是「哪一种卡住会让冻结额永远占着用户可用额」：

| 扫什么 | 判据 | 怎么处置 |
|---|---|---|
| ① `pending` 但次数已用满的 item | `status='pending' AND attempt_count > 0 AND attempt_count >= max_attempts` | 这一张判 `failed`（`DK_MAX_ATTEMPTS_EXCEEDED`）、`fail_count` +1，然后按跟 `FinalizeJob` 一模一样的守卫判一次收尾 |
| ② 心跳过期的批次 | `status IN ('created','holding','running') AND heartbeat_at < NOW() - 10 min` | 转 `failed`、`last_error_code='DK_STALE'`、名下未完成的 item 一并停掉、释放 hold |
| ③ 卡在结算里的批次 | `status='settling' AND settled_at IS NULL AND finished_at < NOW() - 60 min` | 按四个计数算**真实终态**、`actual_cost` 取 `SUM(items.billed_cost)`、写 `settled_at` 封账、释放 hold |

三段的必要性各不相同，别当成一件事：

- **①在拆一个死结。** 领取 SQL 的 pending 支带 `attempt_count < max_attempts`
  （见第六节，那条守卫是对的），代价是这类行**永远领不出来**；
  而心跳按 `status IN ('pending','running')` 算，会让整批**永远续心跳**、
  永远躲过②。批次卡在 `running`，`success+fail+cancelled` 凑不满 `item_count`，
  收尾守卫命中不了，冻结额永远挂着。
  加那条守卫之前这种 job 还能靠心跳停摆被②收走，加了之后不能自愈了，所以必须补①。
  **只判死这一行，不动批次状态**——让心跳「别算它」等于把整批交给②，
  会把同批其它正常排队的 item 全部 `cancelled`，为一行坏数据牵连一整批。
- **③是给「结算 worker 根本没起来」准备的。** `FinalizeJob` 一律把批次写成
  `settling`，而把它推到终态、释放冻结的**只有结算 worker**；而 worker 缺
  对象存储 / 图像处理服务 / 出图网关任意一个就整个不启动
  （`designkit/module.go` 的 `newWorker`）。结算 worker 自己那个 30 分钟的
  强制结算兜底活在结算 goroutine 里，救不了这种情况。
  阈值取 **60 分钟**，比结算 worker 的 30 分钟长一倍：worker 只要活着就该先动手，
  它按已查到的账单算得准；巡检这一档是最后一道，抢在前面只会把账变成粗算。
- **③绝不能一律写 `failed`。** 这批的图很可能全出好了、钱也扣了，只是账没算完。
  标成 `failed` 会让运营照着 `DK_STALE` 的「可以重新提交」为已经拿到手的图
  再花一遍钱。所以终态按 `domain.TerminalJobStatus` 的规则算
  （SQL 里那个 `CASE` 是它的逐条镜像，有单测把两边钉在一起）。
  同理③**不写批次级 `last_error_code`**——出问题的是结算不是出图，
  每张的失败原因本来就在 item 那一行上。

**停机交还租约的预算必须跟 `Stop` 的预算挂钩。**
`Module.Close()` 只给 `worker.Stop` 3 秒，而交还租约那条 UPDATE 走的是
「不受取消影响」的独立 context（默认 10 秒）——既不继承 3 秒、也不会被 Stop 取消。
数据库稍慢就是：Stop 超时返回 → Close 立刻关连接池 → 那条 UPDATE 撞上
`sql: database is closed` → **租约反而没交还成**，在途那几张要挂满 180 秒等租约
自然过期，运营看到「重启完还卡在生成中」。
所以 `Stop` 记下停机截止时刻，写回预算取
`min(WriteBackTimeout, 剩余预算)`，下限 250ms（预算花光也要把 UPDATE 发出去，
发出去还有一半机会赶在连接池关掉之前落库）。

### 5.2 工作台那三个数的口径（决策 16，2026-08-13 定死）

工作台角落显示「本月出图 N 张 / 花费 $X / 余额 $Y」。
**张数和花费是两套口径，而且刻意不统一**：

| 数 | 从哪来 | 时间窗落在哪 |
|---|---|---|
| 张数 | `designkit_images`（排除软删的图） | 图自己的 `created_at` |
| 花费 | `usage_logs`（`request_id LIKE 'client:dki:%'`） | 账单自己的 `created_at` |
| 余额 / 可用额 | `users.balance` − `SUM(open holds)` | 当前值 |

所以运营会看到**「张数是 0，花费不是 0」**。这不是 bug，三种情况都会这样：

1. 出图超时 / 存图失败——上游已经出图扣钱，我们这边没有图（`DK_TIMEOUT` 那一档）；
2. 图被运营自己删掉了（软删），钱花过了不会退；
3. 钱已经扣了、批次还在结算中。

**不统一的理由**：要统一只有两条路，都更糟——
把「已扣钱但没图」的钱从花费里剔掉，运营的账就跟余额对不上（钱确实少了）；
或者把删掉的图算回张数，那删除按钮就成了摆设。
花费的窗口也不能改回按任务算：`job_items.finished_at` **会被重试刷新**，
8 月出的图 9 月点一次重试，整张的钱会跑到 9 月去，月度对账永远对不上。

**所以界面必须写清楚**，这一句是文案的一部分，不是可选的提示：

> 花费按实际扣费统计，包含出图失败但已计费的部分；张数只算还留在作品库里的图，
> 两者对不上是正常的。

落点：工作台那三个数的组件（`frontend/src/features/designkit/`）+
`/usage` 接口的响应里带一个中文说明字段。
后端 `GetUsageSummary`（`repository/billing_repo.go`）不改口径，
它的注释已经写明每一条的理由。

## 六、队列与并发

**领取 item**（一条 SQL，把僵尸回收写进同一个 WHERE）：

```sql
UPDATE designkit_job_items SET
  status='running', worker_id=$1, lease_expires_at=NOW()+INTERVAL '180 seconds',
  attempt_count = attempt_count + 1, started_at = COALESCE(started_at, NOW())
WHERE id = (
  SELECT id FROM designkit_job_items
  WHERE (status='pending' AND available_at <= NOW()
         AND attempt_count < max_attempts)                 -- 次数守卫，只加在这一支
     OR (status='running' AND lease_expires_at < NOW())    -- 僵尸回收，故意不判次数
  ORDER BY job_id, seq
  FOR UPDATE SKIP LOCKED LIMIT 1
) RETURNING *
```

- **`attempt_count` 在领取时就 +1**，不是成功后才加——否则崩一次就永远重试
- 写回结果必须带 `WHERE id=? AND worker_id=? AND status='running'` 并断言
  `RowsAffected = 1`，不等于 1 就**丢弃结果**（说明租约已被别人抢走）
- 租约 180 秒，每 60 秒续

**次数守卫为什么是「一支加、一支不加」**（2026-08-13 补，这里改错会直接烧钱）：

- **pending 支加** `attempt_count < max_attempts`：万一哪天有人写出「把试满的
  item 退回 pending」的代码，这条 WHERE 让它领不出来，也就花不掉钱。
- **僵尸支不能加**：一张 `attempt_count` 已经等于 `max_attempts`、正在跑的图，
  进程被 SIGKILL 之后永远停在 `running`。僵尸支要是也判次数，它**再也领不出来
  = 再也判不了死**，`success+fail+cancelled` 永远凑不满 `item_count`，
  收尾守卫命中不了 → 冻结额永远占着用户余额（运营看到的是「明明没任务
  却提示余额不足」）。
- 所以真正的拦截点在 **worker**：领到 item 的**第一件事**就是判
  `attempt_count > max_attempts`，超了直接判 `failed`（错误码
  `DK_MAX_ATTEMPTS_EXCEEDED`）、**绝不调网关**。
  在这之前是「SQL 不判、worker 也不判 = 没人判」：僵尸每被回收一次
  就先真出一张图花一次钱，才在写回时被判超限。
- 同理，**停机交还租约之前也要判一次次数**。无条件退回 pending 的话，
  已经试满 3 次的图每重启一次就被重领一次、再真出一次图、再扣一次钱
  （滚动更新、OOM 重启都会踩到）。
- ⚠ **pending 支那条守卫自己会造一个死结，必须配一条巡检才完整**：
  一行「`pending` 且已经试满」的 item 从此永远领不出来、永远到不了终态，
  而心跳按 `status IN ('pending','running')` 算，会让整批**永远续心跳**、
  永远躲过僵尸巡检——批次卡在 `running`，冻结额永远占着用户余额。
  **加守卫之前这种 job 还能靠心跳停摆被回收，加了之后不能自愈了。**
  拆结的是 5.1 表里的①（每分钟把这类 item 直接判 `failed`）。
  这两段代码要一起看，改一边必须想到另一边。

**节流**：上游每用户默认 5 并发、每账号 3 并发（`CLAUDE.md` B5）。
我们的并发上限放进 `designkit_settings`，默认 4（留一格给运营的单张操作）。

### 6.1 停止排队（决策 15 的准确落法）

> **⚠v1 错在哪**：v1 只写「取消 = 不再等待，图仍入库」，**没写钱走哪条路**，
> 而且按钮名和真实行为反着。真实状态会是：`usage_logs` 里有 3 笔扣款、
> 我们的 job 是 `cancelled`、`actual_cost` 为空——**凭空多出无归属扣款**。
> 运营点「取消」的动机 100% 是「别再花钱」，他会认为系统失控。
> ERP 光看 `cancelled` 也会误判成「什么都没有，可以重下单」，**直接重复花钱**。

- 接口叫 `POST /jobs/:uid/stop`，按钮叫**「停止排队」**不叫「取消」
- 只做两件事：把 `pending` 的 item 转 `cancelled`、给 job 打 `cancel_requested_at`
- **已 `running` 的 item 必须等自然落地**，job 停在 `running` 直到在途清空，
  然后走**与正常完成完全相同**的结算路径，终态记 `cancelled` 但 `actual_cost` 照实填
- `cancelled_count` 只统计「没开始就被砍掉的」
- ERP 文档写死：**任何终态都必须同时返回 4 个计数，判断有没有图一律看 `success_count` 不看 `status`**

### 6.2 重试

- **重试一张 = 重新出一张图、重新收一次钱**，二次确认并显示单价
- 走与提交同一套准入（单张预估 → `FOR UPDATE` 查可用额 → 不够 422）
- `max_attempts` 默认 3
- `settled_at IS NOT NULL` 的 job 拒绝重试，409 +「这批任务已结算，请重新提交」
- 状态机加 `{succeeded|partially_failed} → running`（仅 retry 触发），
  同事务对 job 行 `FOR UPDATE`、清 `finished_at`、`fail_count` 减 1、`revision` +1
- `actual_cost` 语义 = **所有 attempt 合计**；详情页分开显示「首次 X + 重试 Y」
- retry 也要支持 `Idempotency-Key`（运营双击必然发生）

## 七、Python 预处理服务契约（v1 完全没写）

补边到目标比例是**控制出图比例的唯一手段**，它在出图主链路上。

> **⚠老代码是 fail-open**：`legacy-python` 分支的 `prepare_input_image` 用大 try 兜住，
> 异常就返回原始字节。搬过来就是：补边失败 → 原图什么比例出什么比例 →
> **运营选 3:4 拿回 4:3，钱照扣**，只有一行 warning。

- 独立容器 `designkit-imgsvc`（FastAPI，容器内 8000，**不映射宿主端口**）
- `GET /healthz` 返回 pillow / heif 可用性
- `POST /v1/preprocess` 收 multipart（`file` / `ratio` / `keep_transparency` / `max_dimension`）
  - 成功：**直接返回图片字节**（不要包 JSON base64），元数据放响应头
    （`X-Dk-Changed` / `X-Dk-Width` / `X-Dk-Height` / `X-Dk-Actions`）
  - 失败：JSON 错误码（400/413/415/422 `heif_unsupported`/500）
- **fail-closed**：Python 侧任何异常返 5xx、**绝不回吐原图**；Go 侧非 200 就把该 item 置 failed
- `ratio` 用 `'3:4'` 比例串，Python 侧**新写** `parse_aspect` 直接算整数比——
  老的 `parse_ratio` 只认 `'1536x1024'`，传 `'3:4'` 会**静默不补边**
- `max_dimension` 是显式参数（默认 2048）并存进 `designkit_settings`——
  **它直接决定落 2K 还是 4K 档**，不能埋在 Python 常量里。

  > **⚠ 唯一真相是 `designkit_settings.max_dimension`。** 现在有三份同样的 2048：
  > 数据库预置值、compose 的 `DESIGNKIT_IMGSVC_DEFAULT_MAX_DIMENSION`、Dockerfile 的 `ENV`。
  > 约定死：**Go 侧每次调 `/v1/preprocess` 都必须显式带 `max_dimension` 表单字段**，
  > 值取自 `designkit_settings`；Python 那两个 env 只是「Go 忘了传」的兜底。
  > 不这么约定，管理员把它从 2048 改成 4096 而环境变量没跟着改，
  > 就会「界面说 4K、实际按 2K 出图」——**而且不报错**。

- **出图比例白名单在 Go 侧校验**（读 `designkit_settings.ratios`），不要指望 Python。
  `imgsvc/app/imaging.py` 的 `parse_aspect` **接受任意 `W:H`**（`7:13` 也照收），
  里面的 `SUPPORTED_RATIOS` 常量只用于错误提示文案和 `/healthz` 响应，**不是护栏**。
  Python 是内部服务，不该二次定义业务规则。
- 地址走 `os.Getenv`（`DESIGNKIT_IMGSVC_URL` / `_TOKEN` / `_TIMEOUT_SECONDS`），
  不碰 `config.Config`（不在白名单）
- 图片字节走 body 直传，**Python 服务不接触任何对象存储凭据**
- 只对连接失败和 502/503/504 重试 2 次，4xx 不重试
- **dev compose 的 `NO_PROXY` 必须加 `designkit-imgsvc`**（现有名单只有
  `postgres,redis,sub2api`，网段规则对不上主机名），或给它单独一个 `Proxy=nil` 的 client

### 8.1 超时（`DK_TIMEOUT`）不自动重试（2026-08-13 定，原来是自动重试）

**超时那一张，上游多半已经出图、已经扣过钱了**，只是结果没回到我们手上——
上游调用跟调用方的连接是**故意脱钩**的（`service/openai_images.go` 的
`detachUpstreamContext`，注释写明有意为之），我们这边超时不代表上游停手。

自动重试 = `attempt_count` +1 = 换一个新的 `request_id` = 上游把它当成一次
全新的请求**再收一次钱**。`max_attempts` 默认 3，最坏情况**一张图扣 3 份钱**，
而运营只看到「失败了」。

所以：

- 超时**直接落 `failed`**，错误码保持 `DK_TIMEOUT`（不要换成
  `DK_MAX_ATTEMPTS_EXCEEDED`，运营要能一眼看出这是超时）
- 不进退避重试队列，`available_at` 不推
- 中文文案统一为：
  > 这张图可能已经生成并计费，但我们没收到结果。需要的话可以手动重试（会重新收费）。
- 重试按钮照常给（决策 20 的手动重试，点了二次确认并显示单价）——
  **要不要再花这一次钱，交给人决定，不由系统替他决定**

> ⚠ 这句文案有两处副本，必须一字不差：
> `backend/internal/designkit/domain/errors.go` 里 `DK_TIMEOUT` 那条的 `Message`
> （界面和对外 JSON 真正显示的就是它，按 `last_error_code` 查表），
> 以及 `backend/internal/designkit/worker/errors.go` 的 `timeoutMessage`。

**哪些错误才允许自动重试**（判据只有一条：*重试一次要不要重新花钱*）：

| 错误码 | 自动重试 | 为什么 |
|---|---|---|
| `DK_UPSTREAM_BUSY` / `DK_RATE_LIMITED` | 是 | 图根本没出，不花钱 |
| `DK_UPSTREAM_ERROR` | 是 | 同上，等一会儿可能就好 |
| `DK_NO_AVAILABLE_ACCOUNT` | 是 | 上游账号临时挂了，健康检查恢复就好 |
| `DK_INTERNAL` | 是 | 我们自己这边抖动（数据库、对象存储），发生在调网关之前/之后 |
| **`DK_TIMEOUT`** | **否** | **钱多半已经花了，重试是再花一次** |
| `DK_CONTENT_BLOCKED`、`DK_PREPROCESS_FAILED`、配置类、余额类 | 否 | 重试三次结果一模一样，白烧三张图的钱 |

文档要写明：**出图失败去 designkit 任务详情看，不是去系统监控看**——
重入执行在 `c.Copy()` 副本上，ops 上下文不回流到原始 context。

## 九、必须有的测试

| 测什么 | 为什么 |
|---|---|
| `ORDER BY seq` 守护 | 乱序插 5 个 item，断言返回 1,2,3,4,5。**ERP 契约靠它** |
| request_id 长度 + attempt 维度 | 断言 `len("client:"+id) <= 64`；遍历 attempt |
| **一单 3 张扣 3 份钱** | 含「2 图 × 同 1 词」；断言 3 条不同 request_id 的 usage_logs、余额恰好减 3 张。**入站固定带 `X-Request-Id` 时仍断言 3 条互不相同**（ERP 图省事固定填一个值，会让那把 Key 下所有任务全部塌缩成一条） |
| 重试幂等 | 同 `(seq,attempt)` 重投 3 次只产生 1 条 usage_logs；attempt 1→2 产生 2 条 |
| 计费档混合 | 假上游对 3 张返回 1000/1500/3000 像素，断言各落 1K/2K/4K 且 `actual_cost` = 三档之和 |
| 定价快照 | 结算完改分组定价，断言仍能算出同一个 `actual_cost` |
| 杀进程恢复 | 冻结后 kill worker，断言巡检跑完 hold 归零、job 转 failed |
| **结算卡死也能退钱** | 造一个 `settling` 且 `finished_at` 是 61 分钟前的批次，断言巡检把它判到**真实终态**（不是一律 failed）、写了 `actual_cost` 和 `settled_at`、hold 归零 |
| **pending 死结能自愈** | 造一行「`pending` 且 `attempt_count = max_attempts`」的 item，断言它领不出来、且巡检把它判 `failed` 并让批次继续走到 `settling` |
| **巡检不误伤新任务** | `max_attempts` 写成 0、`attempt_count` 还是 0 的新 item，断言巡检一行都不动（漏了这条，一次坏配置能把全部在排队的图判死） |
| **停机写回预算** | `Stop` 给 3 秒预算时，断言写回 context 的 deadline ≤ 3 秒；预算花光时仍然 > 0 |
| **超时文案两处一致** | 断言 `domain/errors.go` 的 `DK_TIMEOUT` 文案跟 `worker/errors.go` 的 `timeoutMessage` 一字不差 |
| **负差额不放大冻结额** | 反查金额比已回填的小时，断言 `billed_cost` 不变、hold **一分不加**（`GREATEST(amount − 负数, 0)` 会把冻结额加回去，凭空放大可用额） |
| 并发领取 | 多 worker 抢同一 item，断言只有一个拿到 |
| **试满次数的 item 不调网关** | 造一个「attempt 已满、停在 running、租约过期」的僵尸，让它被重新领走，断言**假网关零调用**且直接落 `failed`。少了这条，租约每过期一次就白烧一张图的钱 |
| **停机交还租约判次数** | attempt 已满的在途 item 走 `Stop()`，断言落 `failed` 而不是退回 `pending`。退回去 = 每重启一次多扣一次钱 |
| **超时不进重试队列** | 假网关返回超时，断言落 `failed`、错误码 `DK_TIMEOUT`、`available_at` 没被推、只调过一次网关 |
| worker_id 不匹配丢结果 | 租约被抢走后原 worker 迟到的写回必须被拒（`RowsAffected != 1`），且一张图都不许入库 |
| 计费档巡检 | 断言 `gpt-image-2` 在所有分组下解析出的 Mode **不为 token**（`CLAUDE.md` B2） |
| 假上游 | httptest 返回预置 JSON + 一张真实小 PNG，不联网不花钱 |
| 真枪实弹冒烟 | 5 个比例各 1 张，**记录实际像素填价目表**。只在人为触发时跑 |

### 10.0 ✅ 比例：靠提示词，不靠补白边（2026-08-14 实测）

**原来的设计说「补白边是控制比例的唯一手段」。这句话是错的。**

| 测法 | 请求 | 输入图 | **返回** |
|---|---|---|---|
| 只补白边（改之前） | `1:1` | 554×554（本来就是方的） | **1087×1447 = 3:4** ❌ |
| 补白边 + 提示词里写版式（改之后） | `1:1` | 同一张 | **1254×1254 = 1.000** ✅ |

三条路的真实情况：

| 手段 | 结论 |
|---|---|
| 补白边到目标比例 | 保证**产品不被裁**，但**不保证输出比例** |
| `size` 参数 | 发的是补边后的真实像素（`554x554`），**不是接口认的标准尺寸**，等于没发。仍然发它是因为它决定上游把请求归到 images-native 还是 images-basic 档（`openai_images.go:501` 的 `ExplicitSize`），换掉会改变账号筛选 |
| **提示词里写版式** | **有用**。实现在 `worker/process.go` 的 `withRatioInstruction` |

⚠ **追加的那句话只进发给模型的那一份**，`designkit_job_items.prompt_text`
存的仍是运营写的原文。混同的话历史记录里每条词后面都挂着系统加的话，
运营会以为是自己写的，重试时又会被追加第二遍（有单测钉住这一点）。

⚠ `normalize_input_ratio` 这个开关**在新系统里不存在**，那是老 legacy-python 的
配置名。新系统的补边是无条件的，Python 侧 fail-closed。

9. **⚠ 分布式锁还没接：现在只能跑一个后端实例（2026-08-13 记）。**
   `module.go` 里给出图队列传的 `Locker` 是 `nil`（`worker.AdvisoryLocker` 没有实现），
   启动日志里有一条中文 Warn 说明这件事。
   单副本没有任何问题——群晖上的部署形态就是单副本，这是**已知取舍不是缺陷**。
   但**多副本一上就会出事**：僵尸巡检和结算没有数据库层的互斥，
   两个实例会同时结算同一个批次，而结算会**按张递减冻结额**，跑两遍就多减一次，
   用户的余额凭空少一截，而且**不报任何错**。
   所以下面两件事必须先做完，才允许起第二个实例
   （注意：**滚动更新期间新旧实例会并存**，那一刻也算多副本）：
   - 实现 `worker.AdvisoryLocker`（`pg_try_advisory_lock`；⚠ 它是**会话级**的，
     实现必须从连接池取一条连接一直握着，在同一条连接上 `pg_advisory_unlock`，
     否则锁会跟着连接回池而失效——跟 `SyncRepository.TryLockSync` 是同一个坑）；
   - 在 `module.go` 的 `newWorker()` 里把它传进 `dkworker.Deps.Locker`，
     并把那条启动 Warn 改掉。

   在这之前，部署文档里要写死：**副本数固定 1，不要开滚动更新（用 recreate）**。

10. **出图单价表要靠配置填进去，不改代码**（配合本节第 1 条）。
    实测出每个比例的实际像素和单价之后，管理员往 `designkit_settings` 写两条：
    - `unit_prices`：计费档 → **十进制字符串**金额，例如
      `{"1K":"0.011","2K":"0.042","4K":"0.167"}`（写字符串不写数字，
      JSON 数字是 float64，`0.1+0.2` 会变成 `0.30000000000000004`）；
    - `rate_multiplier`（可选）：报价倍率，默认 1。

    这两条 9001 迁移里**刻意没有预置**。读不到 = 报价接口返回
    `price_confirmed:false`、金额字段为 `null`（界面显示「价格待确认」）。
    ⚠ 后果要知道：**没有单价 = 提交时冻结额记 0 = 拦不住透支**，
    这时候唯一还在守着的是上游每张图出图前那条 `balance <= 0` 的准入。
    所以这一条跟第 1 条一样，是**上线阻塞项**。
